# NY 能力对齐与独立重构基线

日期：2026-10-02  
文档性质：架构与差距基线，不是生产完成声明

同日纠偏更新：当前产品验收以 [NY 业务验收基线](ny-rebuild-acceptance-20261002.md) 为主，
并对照 [官方参考](ny-official-reference-20261002.md)、[现有 NY 只读结构](ny-live-reference-20261002.md)
和 [源码缺口](implementation-gap-20261002.md)。原先第一阶段骨架不能代表 NY 完整体系。
本文件保留架构研究；新机独立试运行已部署，三个旧站未改动，不能沿用早先“未部署/仅内存”的状态。

## 1. 目标纠偏

本项目不是把 VLESS “挂到”现有 NY 面板，也不是让现有鸿乐运营后台代管一套新数据面。目标是从零重构一套可独立安装、独立运行、独立升级和独立恢复的平台：

1. 功能上保留 NY 的用户、节点、入口组、出口组、规则、流量、限制、隧道、批量迁移等核心体系。
2. 在同一套新领域模型中原生增加 VLESS TLS、VLESS Reality、SOCKS5 等客户接入协议。
3. 接入协议、入口设备组、出站方式和公网暴露方式分别建模，允许自由组合。
4. 新平台拥有自己的控制面、数据库、Agent、数据面引擎适配器、API 和可选管理界面。
5. 新平台运行时不依赖 `ht.hongle.work`、`zf.hongle.work`、`kl.hongle.cc`、旧 NY、X-Panel、3x-ui 或 Flux Panel。
6. 旧系统只允许作为版本钉死的、只读的迁移来源。导入完成并切换后，即使旧系统全部不可访问，新平台也必须继续完整运行。

这里的“保留 NY”指业务能力对齐和数据兼容迁移，不是复制未知内部实现，也不是持续代理旧面板接口。NY 没有稳定公开 API 契约和完整公开后端源码，因此长期运行时绑定旧接口会把新系统重新变成旧系统的附属层，与重构目标冲突。

当前仓库只是经过本地验证的第一段纵向骨架，不是完整 NY 重构，更不是可替换生产 NY 的成品。

## 2. 不可突破的保护边界

`zf.hongle.work`、`kl.hongle.cc`、`ht.hongle.work` 当前都属于受保护的既有服务：

- 仅允许只读查看、下载资料或生成离线快照。
- 禁止修改生产配置、重启进程、覆盖部署、改 DNS、改端口、切换流量或写入生产数据库。
- 禁止在三套既有服务或其生产节点上做压测、断网、杀进程、故障注入和回滚演练。
- 本轮不以接管旧机器、复用旧数据库或切换这三个域名为实施前提。
- 所有自动化测试、失败恢复、负载和迁移演练只能在本地或明确隔离的测试环境进行。
- 迁移连接器必须是单向读取；不得提供写回、双向同步或隐式清理旧数据的路径。

因此，任何包含“先改旧面板接口”“先让运营后台提供鉴权”“先在旧节点安装并替换服务”之类前置条件的方案都不符合本项目边界。

## 3. 独立运行边界

```text
运维人员 / API 客户端
          |
          v
新平台 Control API ---- PostgreSQL ---- Worker / Outbox
          |                                  |
          | mTLS                            | 任务与期望状态
          v                                  v
      Edge Agent ---------------------- Xray / upstream GOST
          |                                  |
          +----------- 健康与计量 -----------+

客户 -> ExposurePolicy -> EntryGroup -> IngressProtocol
                                      -> EgressMode -> Internet / ExitGroup / SOCKS

旧 NY / Flux / X-Panel 离线导出
          |
          v
只读 Importer -> Staging -> 校验/差异报告 -> 新平台领域数据
```

新项目中的 `web-admin` 是新平台自己的可替换 API 客户端，不是 `ht.hongle.work`，也不是运行时必需依赖。即使不部署该前端，控制面、Agent 和数据面也应能独立运行。将来若接入其他运营系统，也只能调用新平台的版本化 API，不能反向成为新平台的身份、配置或可用性来源。

## 4. 必须正交的领域模型

### 4.1 四个独立维度

| 维度 | 目标枚举（不代表均已实现） | 负责什么 | 明确不负责什么 |
|---|---|---|---|
| `IngressProtocol` | `TCP_FORWARD`、`UDP_FORWARD`、`SOCKS5`、`VLESS_TLS`、`VLESS_REALITY` | 客户如何接入入口节点 | 选择哪台机器、从哪里出站 |
| `EgressMode` | `DIRECT`、`EXIT_GROUP`、`SOCKS_SINGLE`、`SOCKS_POOL`、`MANAGED_TUNNEL`、`CHAIN` | 流量离开入口后的路径 | 客户凭据和公网入口方式 |
| `NodeRole` | `ENTRY`、`EXIT`、`EDGE`、`HYBRID` | 节点可承担的部署角色 | 自动赋予协议或客户权限 |
| `ExposureMode` | `L4_GATEWAY` | 客户通过一个稳定端点接入，由服务端选择组内机器 | 业务出站路径和节点配置 |

一个可售卖、可发布的服务必须显式组合这些对象：

```text
Service
  = IngressProfile
  + EntryGroup
  + EgressProfile
  + ExposurePolicy
  + CustomerBinding
```

其中：

- `IngressProfile` 保存协议参数、监听策略和密钥引用，不保存明文密钥。
- `EntryGroup` 指定能承载该服务的入口节点集合。
- `EgressProfile` 选择直出、出口组、单 SOCKS、SOCKS 池、受管隧道或链式路径。受管隧道使用公开引擎实现等价业务能力，不宣称与 NY 未公开私有协议兼容。
- `ExposurePolicy` 固定保留一个稳定端点；当前采用 L4，后续补齐其高可用。客户不会收到设备组内的多条节点 URI。
- `CustomerBinding` 绑定客户身份、到期时间、配额和服务权限。

### 4.2 设备组的唯一职责

设备组只负责：

- 节点成员及角色约束；
- 权重、优先级、备用层级和排空状态；
- 能力匹配，例如节点是否安装 Xray、GOST、TCP/UDP 或指定传输；
- 组修订、节点完整配置生成和发布范围；
- 节点健康事实与候选资格的边界。

设备组不得等同于：

- 固定的一台网关；
- VLESS、SOCKS5 或某种协议；
- 客户订阅组或 URI 列表；
- 出站方式；
- 客户身份和配额。

当前代码的 `EndpointPool` 应被视为 `ExposurePolicy=L4_GATEWAY` 下的运行时成员投影，而不是整个新平台的核心业务模型。未来由 `Service` 编译出网关、节点和单链接订阅投影，运维人员不应维护第二份候选成员清单。

### 4.3 用户例子的准确表达

“一个组 10 台机器，客户只有一条 VLESS 链接，每个新连接自动负载，一台挂了其余九台继续”应表达为：

```text
IngressProtocol = VLESS_TLS 或 VLESS_REALITY
EntryGroup      = 10 台 ENTRY/EDGE 节点
EgressMode      = DIRECT
ExposureMode    = L4_GATEWAY（精确按新连接调度）
```

高可用 L4 能让客户保留一条稳定 URI，并在服务端按新连接调度；代价是多一个数据面跳数和网关高可用要求。普通多 A 或健康 DNS 受缓存、TTL 和连接复用影响，不能满足逐连接调度要求，不作为本轮替代实现。任一节点宕机时，该节点上的既有会话仍会断，客户端重连后才能落到健康节点。

## 5. NY 能力保留矩阵

状态含义：

- `REAL_VERIFIED`：已用真实进程或端到端链路在本地隔离环境验证。
- `IMPLEMENTED_LOCAL`：已有代码和自动化测试，但仍是本地开发实现。
- `SKELETON`：只有部分模型、接口或占位实现，闭环未接通。
- `DOCUMENTED_ONLY`：已形成设计要求，尚无实现。
- `MISSING`：当前仓库没有对应实现。

| NY/目标能力 | 新平台必须达到的行为 | 当前状态 | 当前证据与缺口 |
|---|---|---|---|
| 独立管理员登录 | 新平台自己鉴权，不借用旧后台会话 | `IMPLEMENTED_LOCAL` | 新机试运行的登录与 PostgreSQL 快照持久会话已验收；缺完整 RBAC、MFA 和审计管理界面 |
| 节点注册与心跳 | 一次性注册、凭据轮换、能力与资源上报 | `IMPLEMENTED_LOCAL` | 已有一次性令牌、节点凭据和心跳；当前为 Bearer，缺 mTLS、吊销和轮换 |
| 节点角色 | 入口、出口、边缘、混合角色可校验 | `SKELETON` | 已有组种类枚举，尚未用能力约束编译入口/出口任务 |
| 入口设备组 | 组成员共享服务配置，可滚动发布和排空 | `SKELETON` | 成员、权重、优先级和修订已实现；真实引擎发布未接通 |
| 出口设备组 | 多出口最少连接、健康摘除、优先级和备用组 | `MISSING` | 只有 `EXIT` 名称和通用选择器，没有真实出站执行链、备用组和出口探测 |
| 入口直出 | 每个入口节点直接访问目标 | `SKELETON` | VLESS TLS + DIRECT 编译器已存在，但未进入控制面到 Agent 的正式激活链 |
| 传统端口转发规则 | TCP/UDP 监听、目标、端口分配、启停和状态 | `MISSING` | 当前 TCP 网关不是 NY 业务规则管理系统；UDP 未实现 |
| 隧道业务能力对齐 | 通过公开引擎重建隧道承载、连接复用和规则迁移 | `MISSING` | 不得把承载误称为 VLESS；需要独立 GOST 编译器和双端新 Agent，不承诺兼容 NY 私有隧道协议 |
| 反向隧道 | 明确入口/出口方向、鉴权、恢复和限制 | `MISSING` | 尚无模型和引擎链路 |
| 链式出口 | 有限深度、环检测、逐跳健康和失败语义 | `MISSING` | 尚无 `CHAIN` 编译或运行时 |
| 出口故障转移 | 主出口不可用后按策略切备用出口组 | `MISSING` | 通用调度数学不能替代真实出口选择和探测 |
| 规则同步 | 版本化期望状态、确认、失败回滚、离线续跑 | `IMPLEMENTED_LOCAL` | `GroupRevision`、`NodeConfigGeneration`、desired/applied、last-known-good 已有；Agent 目前只激活文件 |
| 控制面失联续跑 | 不清空规则，继续使用最后正常配置 | `IMPLEMENTED_LOCAL` | 本地状态机与原子文件已测试；真实 Xray/GOST 进程恢复未接通 |
| 批量规则导入导出 | 版本化 JSON、预检、差异、幂等和错误隔离 | `SKELETON` | 已有本地 JSON/ZIP 结构预检与脱敏报告；尚无原生业务导入器、staging 表、mapping 或导出 schema |
| NY 数据迁移 | 用户、节点、组、规则、限制和关系可只读导入 | `SKELETON` | 只读预检 CLI 已实现；当前零个 NY 证据适配器，缺原生导入和 `external_mappings`；不猜字段格式 |
| 用户与隧道授权 | 用户只能使用获授权的服务/隧道 | `MISSING` | 当前只有管理员，没有客户和授权模型 |
| 到期与停用 | 到期后跨全部节点撤销且可审计 | `MISSING` | 尚无客户生命周期、撤销任务或全组确认 |
| 流量计量 | 单调序列、重启归零、重复与迟到上报可处理 | `MISSING` | 当前无客户维度 Stats 采集和中央账本 |
| 流量配额 | 跨组聚合后停用，并明确少量超额窗口 | `MISSING` | 尚无配额状态机 |
| 速度限制 | 明确每节点、近似全局或严格全局语义 | `MISSING` | Xray/普通 GOST 无法自动提供严格跨 10 节点总速率 |
| IP/连接数限制 | 明确单节点与跨组限制口径 | `MISSING` | 严格全局限制需要集中协调或统一数据面，不能由普通计数拼接冒充 |
| 多数据库来源兼容 | 可读取 NY 的 SQLite/MySQL/PostgreSQL 导出 | `MISSING` | 新平台自身仍固定以 PostgreSQL 为生产事实库；来源适配器尚无实现 |
| 运行审计 | 所有变更有操作者、幂等键、前后状态和结果 | `SKELETON` | 事件已进入事务快照；缺查询界面、完整幂等覆盖、保留和防篡改策略 |
| 用户组、规则分组 | 资源授权与规则分类独立管理，支持批量工作流 | `MISSING` | 管理员身份和设备组不能代替用户组或规则分组 |
| 倍率与实际流量 | 区分规则原始用量、用户扣量、组统计 | `MISSING` | 入口/出口倍率与去重账本尚无实现 |
| 多目标与用户自带出口 | 独立目标池和授权，保留原有出站选择 | `MISSING` | 不能由单一端点池概念替代；原生字段待版本化证据 |
| 节点对接与探针 | 组内安装流程、在线/离线安装、版本/资源/失败定位 | `SKELETON` | 注册令牌不等于一键安装，心跳字典不等于完整探针 |
| 商业与推送领域 | 商店、套餐、充值、续费、订单、支付、兑换、邀请、返利、推送与 Telegram | `EXCLUDED` | 操作者已明确排除整个领域；不得留下死入口、字段、权限或指标 |

NY 的已知边界也必须原样记录，不能在重构中被误包装为现成功能：

- NY 入口设备组共享规则，但不负责客户到多入口机的负载均衡。
- NY 的 `ws/http/tls` 是自研 TCP 隧道承载，不是 VLESS。
- 会终止 TLS/SNI 的 NY 链路不能透明承载 Reality；只有不解密的 L4 透明路径才可能放在 Reality 前面。
- NY 的速度、IP 数和连接数明确按每台入口节点独立计算，并叠加用户级与规则级限制，不是跨组严格全局口径。
- NY 官方明确 UDP 不支持速度、IP 数和连接数限制；迁移时必须逐条标注，不得静默降级。

## 6. 新增协议与出站组合矩阵

下表描述目标可组合性，不代表当前已经实现：

| 接入协议 \ 出站模式 | `DIRECT` | `EXIT_GROUP` | `SOCKS_SINGLE` | `SOCKS_POOL` | `MANAGED_TUNNEL` | `CHAIN` |
|---|---|---|---|---|---|---|
| `TCP_FORWARD` / `UDP_FORWARD` | 必须保留 | 必须保留 | 需验证传输支持 | 需验证传输支持 | 重建等价业务，逐项验证传输 | 有限支持，需环检测 |
| `SOCKS5` | 必须支持 | 必须支持 | 无必要，除非做上游代理 | 必须支持 | 可选 | 可选 |
| `VLESS_TLS` | 首个正式闭环 | 必须支持 | 必须支持 | 必须支持并健康切换 | 仅隔离 PoC | 可选，逐跳验证 |
| `VLESS_REALITY` | 必须支持 | 必须支持 | 必须支持 | 必须支持并健康切换 | 禁止经过会终止 Reality 的旧链路 | 仅透明 L4 或原生 Xray 链 |

组合验证必须至少覆盖：

- 引擎是否支持 TCP 与 UDP；
- 入口真实 IP、DNS、SNI、TLS/Reality 是否在中间层丢失；
- 流量由哪一跳计量，是否会重复计费；
- 主出站、备用出站和全部失败时的行为；
- 客户撤销是否在所有可达入口生效；
- 链式路径的最大深度、环路和逐跳超时；
- 控制面失联后是否继续使用最后正常配置。

不得用一个 `protocol` 字段同时表达接入协议和隧道传输，也不得用一个 `group_id` 同时代替入口组、出口组和客户订阅。

## 7. VLESS 与设备组的关键规则

### 7.1 VLESS TLS

- 同一稳定 URI 可以通过高可用 L4 转发到多个持有同一客户身份的 Xray 入口。
- 节点证书、私钥和客户 UUID 只能经授权秘密分发，不能出现在列表 API、日志或审计详情中。
- 客户身份新增、停用和撤销必须形成全组任务，并记录每台节点的确认状态。
- 未确认撤销的节点必须被隔离，不能继续作为候选。

### 7.2 VLESS Reality

- 若单 URI 指向多个后端，后端需要兼容的服务端身份；共享组级私钥会扩大泄露范围，必须使用独立密钥版本、最小分发范围和快速轮换。
- 单 URI 的产品要求已经确定，不能以多节点订阅规避密钥设计。未来若要求每台节点使用独立 Reality 私钥，需要重新评估受控终止入口；在方案验证前，拒绝无法用同一 URI 认证的组配置。
- 普通 TLS/SNI 代理不能终止 Reality 后再转发，L4 网关只能透明传递原始 TCP。

### 7.3 健康与调度

- Agent 心跳只证明 Agent 可达，不能证明 VLESS 握手、目标出站或出口 IP 正常。
- 候选资格需要协议握手探测、目标出站探测和未过期健康租约。
- `draining` 只停止接收新连接；已有连接自然结束。
- 健康恢复需要连续成功阈值和防抖，不能一次成功就直接恢复生产流量。
- 选中后拨号失败可以触发同一新连接的有界重试，但不能无限重试或跨服务泄露凭据。

## 8. Flux Panel 源码核验结论

本地只读核验的 Flux Panel main HEAD 为 `9b5ccdb1f428454695bd81c034324aaa58eb91b8`。它可作为行为参考，不适合作为本项目的领域底座。

### 8.1 可借鉴的事实

- Spring Boot 侧明确拆分 `Node`、`Tunnel`、`Forward`、`UserTunnel`、`SpeedLimit` 和 `StatisticsFlow`。
- `Tunnel` 使用单个 `inNodeId` 和单个 `outNodeId`；`Forward` 绑定单个 `tunnelId`，因此不是 NY 式入口组/出口组模型。
- `remoteAddr` 可保存逗号分隔的多个目标；改造 GOST 使用 `fifo/round/random/hash` 选择器、失败过滤和备用过滤。
- 创建转发时会建立入口服务、链和远程服务，可借鉴“业务对象编译成多个数据面资源”的分层思想。
- GOST 服务能统计当前连接、总连接、上下行字节和错误，并向控制端上报，可借鉴计量字段但不能直接照搬协议。
- 根仓库为 Apache-2.0，可依法参考或复用明确适用的代码，但新平台仍应维持清晰的第三方清单和修改记录。

### 8.2 不能照搬的部分

- 没有 VLESS、Xray、Reality、入口设备组、出口设备组或稳定客户端点模型。
- `Tunnel` 的单入口/单出口关系无法表达组级调度、备用出口和服务组合。
- 控制端以逐项 WebSocket 命令直接修改 GOST，缺少持久 desired/applied generation、完整节点配置和可靠 outbox。
- 单服务更新代码会先关闭并注销旧服务，再解析和注册新服务；失败时不能等价保证上一代原子存活。
- GOST 选择器主要依赖拨号失败后的被动过滤，不等于主动的协议握手和真实出站健康检查。
- 流量上报地址使用明文 HTTP，并把 `secret` 放在查询字符串；AES 初始化或加密失败时还会退回发送原始 JSON。该安全行为禁止进入新平台。
- 面板的批量操作和局部回滚不能替代跨节点发布、隔离、撤销确认和 last-known-good。

结论：可以复用或重写的最小部分是 upstream GOST 的成熟转发、链、选择器和统计能力；Flux 的业务模型只能作为迁移映射输入，不能成为新平台领域模型。

## 9. NY 只读迁移模型

### 9.1 边界

- 迁移器是独立 CLI 或一次性 Job，不属于新平台在线请求链。
- 优先读取经过校验的导出文件；确需调用旧接口时必须版本钉死、只读、限速并保留响应快照。
- 不向旧系统写回，不自动删除旧规则，不在旧机器安装或替换 Agent。
- 导入完成后关闭旧源访问，新平台只读取自己的 PostgreSQL。

### 9.2 必要数据结构

| 对象 | 作用 |
|---|---|
| `import_batches` | 来源、版本、快照哈希、开始/结束时间和总状态 |
| `import_staging_records` | 保存规范化前的受控原始记录及逐条错误 |
| `external_mappings` | `source_system/source_panel_id/external_type/external_id` 到新 ID 的唯一映射 |
| `import_decisions` | 冲突、跳过、替换、人工映射和不支持项的审计 |
| `migration_checkpoints` | 可恢复进度，保证重复运行幂等 |

`external_mappings` 至少保存 `import_revision`、`content_hash` 和 `last_seen_at`。同一批次重复导入必须得到相同结果；同一外部 ID 内容变化必须生成可审核差异，不能静默覆盖。

### 9.3 流程

```text
获取只读快照
  -> 校验来源版本与整体哈希
  -> 写入 staging
  -> 解析并规范化
  -> 建立用户/节点/组/规则依赖图
  -> 检查端口、引用、协议和能力冲突
  -> 生成 dry-run 差异与不支持项
  -> 人工批准
  -> 事务写入新模型
  -> 在隔离节点编译并验证配置
  -> 对账数量、关系、流量口径和抽样链路
```

旧密码、节点密钥和代理凭据若无法确认算法或安全性，不得原样继续使用；应导入为“待重置/待重新注册”。原始快照需要加密保存、限定访问并记录 SHA-256，日志中不得回显秘密。

## 11. 分阶段重构顺序与完成门槛

### 阶段 0：冻结模型与保护边界

- 冻结本文件的正交模型、状态词汇和受保护系统清单。
- 建立 NY/Flux 脱敏 golden fixtures 和导入契约测试。
- 建立第三方许可证清单、威胁模型和秘密分类。

完成门槛：不存在需要旧后台在线参与的新平台业务流程；所有测试数据均来自隔离夹具。

### 阶段 1：可持久的独立控制面

- 实现 PostgreSQL repositories、迁移回滚、事务 outbox、worker 和幂等请求。
- 实现管理员 RBAC/MFA、持久审计、密钥引用和备份恢复演练。
- 节点改为 mTLS 注册、吊销和轮换。

完成门槛：重启所有新平台组件后状态不丢失；数据库恢复和节点证书轮换在隔离环境通过。

### 阶段 2：NY 传统转发能力闭环

- 实现客户、授权、节点能力、端口池、传统转发、入口/出口组、直出、备用出口组。
- 编译 upstream GOST 配置，不复用 Flux 的不安全上报和逐命令状态模型。
- 实现 TCP 后再逐项验证 UDP，所有降级显式标记。

完成门槛：传统规则从创建、发布、健康、计量、停用到恢复全部端到端可验证。

### 阶段 3：VLESS 原生接入

- 实现客户 UUID 生命周期、VLESS TLS、Reality、订阅签发、撤销和密钥轮换。
- `IngressProfile` 与 `EgressProfile` 独立编译。
- 全组发布失败时保留上一代，并隔离未确认节点。

完成门槛：新建、续期、停用、撤销和轮换在全部组成员上有一致确认；错误配置不能破坏上一代。

### 阶段 4：暴露与健康调度

- 接通控制面到网关的版本化成员快照。
- 实现协议握手、目标出站、出口 IP 和区域探针。
- 实现双活 L4，验证单一稳定端点的故障恢复；不以 DNS 近似分散替代逐连接调度。

完成门槛：节点失败、进程失败、网络失败和探针失败在隔离环境自动摘除恢复；控制面中断不影响已运行服务。

### 阶段 5：计量与限制

- 实现按客户、服务、节点和方向的单调计量账本。
- 实现配额、到期、每节点限制和明确标注的近似全局限制。
- 严格全局速率/IP/连接数另设数据面项目，不以轮询统计冒充。

完成门槛：重启归零、重复、乱序、迟到和部分节点离线场景对账通过。

### 阶段 6：只读迁移与切换准备

- 完成 NY/Flux 版本化导入适配器、dry-run、冲突处理、可重复对账。
- 在隔离环境完成全量演练、回滚包和运行手册。
- 生产切换必须另行授权，且不得默认使用或改动三个受保护域名。

完成门槛：迁移数量、引用关系、抽样规则和真实协议链路全部对账；未支持项为零或有逐项批准记录。
