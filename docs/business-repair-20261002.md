# NY 业务修补与界面对齐验收

日期：2026-10-02。独立项目：`ny-vless-platform`；目标站点：`https://xzf.hongle.cc`。

本文记录本轮实际增量，不能据此宣称已经完整实现 NY、客户 VLESS 开通或正式跨机转发。

## 已接入的业务模块

- 用户：创建、编辑、密码哈希、用户组、启停、到期时间、流量额度、规则数量及限速/IP/连接数策略。
- 用户组：入口与出口设备组授权、入口直出许可、编辑修订检查。
- 设备组网络：连接地址、端口范围、入口直出策略、允许出口及流量倍率。
- 转发规则：用户归属、必选入口/转发组、入口直出或经出口组、TCP/UDP、监听端口、结构化多目标、目标选择策略、编辑/复制/暂停/恢复。
- PostgreSQL 持久化：四个领域的读写、成功审计和幂等结果一起提交；兼容旧 v1 快照并在首次写入（包括管理员登录创建会话）升级到 v2。

新建规则会检查双方授权、用户状态及规则数量；端口分配在事务中进行。暂停规则保留端口。不同入口组共用一台机器时，同协议、同端口也视为冲突；后续添加组成员同样检查冲突。TCP 和 UDP 使用独立端口空间。

路径语义固定为：入口直出是“客户 -> 入口/转发组 -> 目标”，经出口组是“客户 -> 前置入口组 -> 出口组 -> 目标”。直接转发同样必须选择转发组；它只是不再选择独立出口组。`EXIT_GROUP` 也不能单凭名称认定为专线，公网隧道和专线属于底层承载配置；在独立线路模型和真实执行链接通前，界面不得把保存的出口组关系描述成已建成专线。

所有新业务 API 都要求现有管理员会话；写操作需要 `Idempotency-Key`，更新需要当前 `revision`。同一请求重试不会重复创建记录；旧修订不能覆盖新修改。空密码编辑在事务内保留最新哈希，避免并发密码重置被旧数据覆盖。

用户组收权、客户转组或缩小网络端口范围不能静默使已有规则失效，冲突返回 409。当前尚无规则删除功能，应通过编辑迁移相关规则后再调整授权。

## 界面参照

本轮实际登录 `zf.hongle.work`，只读查看了转发规则、用户管理、用户组管理和设备组管理；打开新建弹窗查看字段，并全部取消，未提交业务表单。登录会产生原站正常会话/访问日志。

参照为 64px 顶栏、约 224px 白色侧栏、紧凑工具栏和表格、约 416px 单列弹窗、右下角取消/确定、高级选项折叠。规则表单不再直接暴露 `customer_id`；管理员先在独立步骤选择客户，进入规则表单后归属锁定。未实现的原站操作不放可误点的假按钮。

原站转发规则新建顺序：名称、入口、监听端口、每行一个目标地址、高级选项。管理列表以用户、用户组、设备组、转发规则为核心，去除“服务端点”、`EDGE/HYBRID` 新建入口、原始配置发布等内部原型操作。

## 必须区分的未完成项

保存规则不等于真实转发。当前新增规则保持 `pending_activation`，不会因为写入成功显示“运行中”。新业务规则自动下发到真实 Agent、正式节点安装及引擎生命周期、VLESS 客户凭据/证书/单一 URI、出口链路、流量采集与实时限额仍未接成业务闭环。

GOST 编译子集支持 TCP DIRECT；UDP 和 EXIT_GROUP 的表单及存储已存在，但该编译器明确拒绝未验证的激活路径。客户登录门户和 NY 原生导入等仍在差距清单内；套餐订单属于最新范围明确排除的商业领域。

## 发布与回滚

发布状态：尚未执行本轮切换。

候选目录计划为 `/opt/nyvp/releases/20261002-business-nyui`，原版本为 `/opt/nyvp/releases/20261002-initial`。脚本先对备份副本运行新版 API，并核对管理员登录、所有旧/新列表接口和重启保留会话。

正式切换前短暂停止新面板 API，做最终数据库备份，在本机临时监听上验证真实数据库迁移，再开放新版本。此时只涉及 xzf；不变更 DNS、网关、防火墙、TLS，也不操作三个受保护旧站的服务配置。

旧程序不支持 v2 快照。已开放公网写入后，不能只切回旧程序，也不能盲目恢复旧备份覆盖新数据；应优先用兼容 v2 的版本修复。确需成套回滚，必须先停止写入、备份最新状态，并评估部署后新增记录，再恢复匹配的旧程序与数据库。
